原生配套程式 API

適用於任何助理的原生整合

為任何助理打造原生配套程式。你的應用程式掌管自己的對話與模型連線；OpenWalkieTalkie 提供分組的裝置清單、語音輸入、對話顯示、提問與工作階段設定。Conol 使用的也是同一個公開介面。

需要 0.11.0 或更新版本的 OpenWalkieTalkie 應用程式、服務與韌體。這是透過 JSON-RPC 的本機桌面整合，不依賴 Conol。現有的 CLI 掛鉤仍然支援。

試用範例

啟動 OpenWalkieTalkie，連接裝置，下載範例，然後執行：

python3 native_companion.py

Python 3.10+ 就夠了，不需要任何套件或憑證。選擇 Example → + New chat，口述第一則訊息，新的對話就會在裝置上開啟。說「form」可以試試分頁的單選題、多選、口述文字與最後的檢閱。開啟工作階段設定，可以在兩個預先寫好的示範模型及其思考強度選項之間切換。範例不會呼叫任何模型 API。按 Ctrl-C 會釋放它的註冊。

範例中的 Companion.order、Companion.apply_settings 與表單送出的分支，就是接上你的後端的地方。它在記憶體中保存一小段對話記錄與表單草稿；正式的應用程式應從自己的對話儲存中還原這些內容。一次只執行一個示範，因為兩份複本都使用「Example」裝置標題。

連線與探索

從你的桌面程序連線到同一使用者的 Unix 網域通訊端。每一行傳送一個 UTF-8 JSON-RPC 2.0 物件，每個請求使用不同的 id。依 id 對應回覆；通知可能夾在回覆之間抵達。後端處理進行中時，請持續傳送心跳。

  • 自訂路徑：如果已設定環境變數 DECKD_DATA_DIR，通訊端位於 $DECKD_DATA_DIR/deckd.sock。
  • macOS：~/Library/Application Support/OpenWalkieTalkie/deckd.sock。
  • Linux：${XDG_DATA_HOME:-~/.local/share}/openwalkietalkie/deckd.sock，也就是 Omarchy 安裝用來執行服務的資料夾。Linux 是服務、Omarchy 橋接與配套應用程式都支援的平台（見 Omarchy 指南）。

每次連線都以此開始：

{"jsonrpc":"2.0","id":1,"method":"session.hello","params":{
  "client":{"name":"Example companion","version":"1"},
  "scopes":["agent","observe"],
  "subscribe":["agent.order","agent.answer","focus.changed","session.settings_requested"],
  "snapshot":false
}}

通訊端會驗證本機作業系統使用者。這個整合只請求 agent 與 observe。你擁有的事件包含處理你的對話所需的內容；這些權限範圍不會讓你取得其他應用程式的私人對話記錄。不需要傳送任何遠端 API 金鑰給常駐程式。請把通訊端留在受信任的桌面程序中，不要把原始的 RPC 橋接暴露給網頁內容。

通訊端不存在代表服務無法使用：請顯示未連線狀態，並以退避方式重試。如果兩個新方法中任一個回傳 -32601，表示常駐程式不支援原生配套程式；請提示更新，而不是悄悄回報整合已連線。各個方法、權限範圍與請求結構描述都在 API 參考資料中。

通訊端是已連線應用程式唯一的入口。服務在 127.0.0.1 上的 HTTP 與 WebSocket 入口，以及開啟它的持有人權杖，預設都是關閉的。只有在舊版 OpenWalkieTalkie 安裝留下的 Claude Code HTTP 掛鉤仍需要時，服務才會讓這個入口保持開啟；config.toml 中明確的 [api] tcp 設定一律優先。下一個版本預計移除這個入口與它的權杖。請不要以它們為基礎開發。

註冊工作階段並分組

每個對話註冊一個助理，另外可選擇註冊一個啟動器。為每個應用程式/帳號/對話保留穩定且具命名空間的 key。在同一條連線上重複註冊相同的 key，結果相同。

{"jsonrpc":"2.0","id":2,"method":"agent.register","params":{
  "kind":"other","name":"Plan the release","key":"example:personal:chat-42",
  "caps":{"answer":"push","order":"push","focus":true},"lease_ttl_s":30
}}

保存回傳的 agent ID，之後的請求都會用到。以下範例以 ag_example 作為預留位置。

{"jsonrpc":"2.0","id":3,"method":"agent.companion.set","params":{
  "agent":"ag_example","profile":{
    "app_id":"org.example.companion","group_id":"personal",
    "group_label":"Example","role":"session"
  }
}}

app_id 是穩定的應用程式識別碼（1–64 個 ASCII 字母、數字、句點、連字號或底線）。group_id 識別應用程式中的一個帳號或工作區（1–128 個 UTF-8 位元組）。group_label 是它顯示的標題（1–24 個 UTF-8 位元組）。標籤與 ID 不能為空，也不能包含控制字元。這些是公開的顯示欄位：請使用不透明的帳號 ID，而不是憑證或私人帳號名稱。若分組應該在裝置上分成不同頁，請使用不同的標籤，例如「Example · Work」：韌體依顯示的標籤分組；桌面端的分組與溢出提升則使用應用程式/帳號 ID。

role 是 session 或 launcher。profile: null 會移除原生的呈現方式。在 API 中，kind 仍代表服務供應商身分；自訂助理請用 other。現有的服務供應商類型也接受配套程式設定檔。Conol 選用的機器人圖像來自它的 kind；其他應用程式整合時既不需要這個圖像，也不需要新的韌體列舉值。

原生焦點透過事件傳給你的應用程式，而不是對終端機注入輸入。共有八個共用的實體槽位。請檢查回傳的 slot（null 代表溢出）。聚焦一個溢出的配套程式時，會先以一般方式分配槽位；若所有槽位都在使用中，它可以取代同一所屬連線、同一應用程式與同一分組中一個未釘選的工作階段。這個備援會保留啟動器、其他帳號與其他應用程式。所有候選都受保護時，它不保證能取得槽位。不要把所有歷史工作階段都註冊進來：只發布近期仍在使用的工作階段，完整清單保存在你自己的應用程式裡。

每 10 秒傳送一次帶有你所擁有助理 ID 的 agent.heartbeat，以維持 30 秒的租約。登出或關閉時，使用 agent.release。通訊端中斷後，重新連線並再次註冊。如果註冊回傳擁有權衝突 -32004，agent.claim {"key":"…"} 可以收回孤立或已過期的註冊；它無法接管仍在使用中的連線。重新連線後，請重新發布設定檔、設定、對話記錄與目前的提問。租約和常駐程式都不是你的永久聊天資料庫。

開始並啟用新的聊天

註冊一個名為 + New chat 的啟動器，使用 role: "launcher"，並與它的對話使用同一個分組。它的指令能力必須是 push。角色控制呈現方式與槽位保護；它不會替你建立後端工作階段。

依下列格式處理通知：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"agent.order","rev":123,
  "data":{"agent":"ag_launcher","text":"Help me plan the release","order":"or_12"}
}}
  1. 把 data.agent 對應到你擁有的帳號與啟動器。在這個連線內，以通知的 rev 與 type 去除重複。
  2. 透過你經過驗證的後端建立對話與第一則使用者訊息。保存它的永久 ID；同一個啟動器的並行建立要依序處理。
  3. 以新對話自己的穩定 key 與 role: "session" 註冊它。發布實際的設定與最近的訊息。
  4. 在你的應用程式中選取新對話，然後呼叫 agent.focus {"agent":"ag_new"}。常駐程式會在聚焦前送出槽位取代的更新，韌體會在放開 PTT 後開啟該對話。已經開啟的提問卡片維持不動。

處理帶有 data.source: "device" 的 focus.changed 時，請在你的應用程式中選取對應的對話，或為啟動器開啟空白的輸入框。不要再回應另一個聚焦請求，以免形成回饋迴圈。未知助理 ID 的事件必須忽略。

絕對不要盲目重試結果不明的後端建立。請使用後端的防止重複建立的識別碼（idempotency key），或先核對永久保存的結果。通訊端重新連線不能證明先前的建立失敗了。範例中的本機記憶體建立只是示意；正式的後端必須提供這項保證。

讓兩邊的對話記錄保持最新

對於已有的工作階段，agent.order 代表傳送一則後續訊息給該對話。請在後端使用穩定的用戶端訊息 ID，更新應用程式中可見的對話記錄，並恢復它的回應串流。只同步到裝置，會讓你的桌面介面過時。

每個為你的助理口述或輸入的指令，都在 data.order 中帶有一個指令 ID；在你的完成卡片上選擇的步驟（ctx: "step"）則不帶 ID，也不需要回報。如果訊息無法送達你的對話，請回報，裝置就會顯示該指令未送達：

{"jsonrpc":"2.0","id":5,"method":"agent.order.result","params":{
  "agent":"ag_example","order":"or_12","ok":false,"reason":"backend_refused"
}}

reason 是由小寫字母、數字與底線組成的一個詞，最多 32 位元組。每個指令最多回報一次，且須在十分鐘內；ok: true 會被接受，但不會改變任何東西。回覆為 {rev, shown}，其中 shown 為 card、toast 或 none。常駐程式因此放到你的助理上的卡片，會以帶有 host: "failure" 的 card.set 送達；你的下一次 agent.card.set 會取代它。如果它取代了你的一張資訊卡片（沒有任何東西在等待的卡片），對那張卡片的 agent.card.clear 仍會得到 {rev} 回覆，而失敗卡片維持不變。較舊的常駐程式不會傳送 order，並回覆 -32601：此時略過回報即可。這個方法存在時，service.info 會在 capabilities 中列出 order.result。

以穩定的 ID 發布公開的使用者訊息與助理訊息：

{"jsonrpc":"2.0","id":4,"method":"agent.reply","params":{
  "agent":"ag_example","text":"I can help with the release.","speak":false,
  "message":{"id":"message-42","role":"assistant","streaming":true}
}}

串流時，用同一個訊息 ID 傳送即可取代文字；最後以 streaming: false 結束。使用者訊息也以 role: "user" 傳送。常駐程式為每個助理最多保留 64 則訊息與 512 KiB；請發布數量有限的近期訊息。不要把私人的推理過程、憑證與內部工具引數放進同步的對話記錄。朗讀需透過 speak 主動開啟。

用 agent.update 設定對話名稱、短標題與 state（working、question、ready、error 或 idle）。保持後端的實際狀態，如實顯示傳送失敗，不要宣稱訊息已被接受。回應結束時，先發布它的最終訊息（streaming: false），再設定 state: ready：狀態變為 ready 時，裝置會朗讀已有的回覆，但絕不會朗讀對話上一次變為 working 之前發布的回覆。

原生配套程式也可以透過 agent.reply 發布公開的工具活動：使用 message.role: "tool"、明確的 activity（running、completed、failed 或 stopped），以及 summary: {"label":"Running a command","detail":"cargo test"}。這個選用的摘要需要結構描述中含有 ActivitySummary 的新版常駐程式；0.11.0 韌體可以顯示產生的列。請使用穩定的呼叫 ID，只在執行期間設定 streaming，並在上一個呼叫消失時將它結束或停止。只傳送可見的標籤與預覽，完整的工具輸入/結果留在所屬的應用程式中，並保持 speak: false。摘要內容和對話文字一樣，依內容權限範圍進行遮蔽。

用你自己的語音模型轉寫

如果你的應用程式有自己的語音辨識器，請以 caps.transcribe: "push" 註冊。之後常駐程式會錄下每一次對該助理的按住說話，並在使用者放開 PTT 時提供給你的連線。你回傳的文字會成為這次按鍵的最終轉寫，因此裝置上的轉寫、agent.order 與口述的 agent.answer 都會使用它。常駐程式自己的辨識器仍會同時執行；若你失敗、拒絕、傳送空白文字、中斷連線或超過 20 秒，就由它提供最終轉寫。按住期間不會顯示它辨識出的文字，因為那不是最後要傳送的內容。裝置會改為顯示隨麥克風音量變化的 RECORDING 波形（需新版韌體；舊版韌體顯示空白的轉寫）。舊版常駐程式會忽略這個欄位。如果需要事先知道，請檢查 service.info 的 capabilities 是否包含 transcribe.companion。

{"jsonrpc":"2.0","method":"event","params":{
  "type":"agent.transcribe","rev":124,
  "data":{"agent":"ag_example","transcription":"tr_7","mime":"audio/wav",
    "rate":16000,"ms":4200,"bytes":134444,"page":98304,"locale":"en-US"}
}}

錄音為 16 kHz、16 位元單聲道 WAV，最長約一分鐘。用 agent.transcribe.audio {"transcription":"tr_7","offset":0} 分頁取得，它會回傳 {offset,total,data}，其中 data 為 base64。依解碼後的長度推進 offset，直到等於 total。接著以 agent.transcribe.result {"transcription":"tr_7","text":"…"} 回覆且只回覆一次；若無法轉寫，則以 "error":"…" 回覆。出錯時請立即回覆，不要保持沉默，裝置才不必等到時限用完。只有所屬的連線可以讀取或回覆這個請求。請求只會傳給該連線，絕不會出現在事件匯流排上。用來替裝置本身命名的錄音，以及按住不到 0.3 秒的錄音，都不會提供給應用程式。只有 [voice.stt] companion 開啟時（預設開啟），音訊才會離開常駐程式，使用者可以關閉它。

在裝置上處理複雜提問

公開的提問基本元件是 agent.card.set。一張卡片最多有四個選項，並可選擇允許自由文字。請在你的應用程式中建立多步驟表單；每顯示一個步驟都使用新的卡片 ID。

{"jsonrpc":"2.0","id":5,"method":"agent.card.set","params":{
  "agent":"ag_example","type":"q","text":"1/3 Choose a language",
  "choices":[{"label":"Python"},{"label":"Rust"},{"label":"More"},{"label":"Cancel"}],
  "free_text":false,"deliver":"push","origin":{"kind":"custom"}
}}

保存 result.card.id。只有在 data.agent 與 data.card 都與目前的提問相符時，才接受 agent.answer。data.choice 是從零開始的選項索引；data.text 帶有口述的自由文字。絕對不要把遲到的回答套用到取代後的提問上。發布下一步之前，用 agent.card.clear {"agent":"…","card":17,"delivered":false} 清除上一張卡片。

  • 選項清單太長時分頁顯示，而不是截斷。把按鍵留給導覽。
  • 多選以切換方式實作，翻頁時保留已選項目，直到 Next。
  • 輸入/口述的回答或「其他」選項，請使用專用的 free_text: true 步驟。
  • 草稿保存在本機。用 Submit、Edit 與 Cancel 檢閱完整的回答。
  • 只有 Submit 會把回答送給後端中那個正在等待的工具呼叫或核准。導覽、編輯與取消都不能核准任何東西。
  • 只有在後端接受送出後才確認送達。失敗時保留草稿，並在明確重試時重複使用同一個穩定的送出 ID。重新連線後，再次確認後端的提問仍在等待中。

如果表單無法在裝置的限制內呈現，請提供明確的「在應用程式中開啟」選項。應用程式應聚焦到相關的提問，而不是假裝表單已完成。範例以一個預先寫好的本機表單示範這個精靈；Conol 則把同樣的模式接到 AskUser 與工作流程核准上。

顯示並變更模型 / 思考強度

用 agent.session.set 為你擁有的任何助理回報設定。只供顯示的設定不需要目錄：

{"jsonrpc":"2.0","id":6,"method":"agent.session.set","params":{
  "agent":"ag_example","controls":{
    "model":"My model","effort":"High","editable":false,
    "note":"Change these settings in Example."
  }
}}

對於可在裝置上編輯的設定，請提供穩定的模型 ID、易讀的標籤，以及每個模型支援的思考強度值。傳送後端實際的選擇，而不是猜測的預設值。

{"jsonrpc":"2.0","id":7,"method":"agent.session.set","params":{
  "agent":"ag_example","controls":{
    "model":"fast","effort":"low","editable":true,"note":"",
    "models":[
      {"id":"fast","label":"Fast model","efforts":["low","high"],"default_effort":"low"},
      {"id":"simple","label":"Simple model","efforts":[],"default_effort":""}
    ]
  }
}}

model 以及每個模型的 ID/標籤，最長 128 個 UTF-8 位元組；思考強度字串最長 32；note 最長 256。最多 64 個模型，每個模型最多 16 個思考強度，模型 ID 與思考強度值都必須唯一。控制字元會被拒絕。可編輯的選擇必須屬於它的目錄；空的思考強度代表後端預設值或沒有思考強度設定。非空的 default_effort 必須列在該模型的思考強度中。

在裝置上選擇會發出 session.settings_requested（requested 前面是底線）：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"session.settings_requested","rev":124,
  "data":{"agent":"ag_example","model":"fast","effort":"high","request_rev":19}
}}

在後端套用所請求的設定，然後呼叫 agent.session.set，帶上實際得到的控制項與 request_rev: 19。請使用 data.request_rev，而不是外層事件的 rev。裝置會讓現有的選擇保持待定，直到收到確認。失敗時，以一則簡短說明的 note 確認未改變的實際設定。

一般的重新整理不帶 request_rev，也不會了結待定的請求。不相符、重複或過期的確認會被拒絕。待定的變更在 45 秒後逾時。在非同步處理中保持請求與助理的對應，若回應遺失，請與後端核對。常駐程式驗證傳輸與擁有權；授權並套用模型變更仍是你的應用程式的責任。

為 Omarchy 頁面提供資料

裝置的 Omarchy 頁面是一個視窗切換器：一列最多九個工作區標籤，以及最多六列視窗。其中沒有任何東西是 Omarchy 專屬的。任何應用程式都可以用 device.ws.set 填入內容，並透過三個事件回應使用者在那裡的操作。Omarchy 橋接（原始碼儲存庫中的 host/omarchy/）是參考用戶端，CI 會在每次有人提出 pull request 時執行這些測試。

頁面資料是公開介面，從現在起只增不減。device.ws.set 以及 device.ws、device.key 與 device.link 事件可能會新增欄位；現有欄位都不會被重新命名、改變型別或移除。請忽略你不認得的欄位。

請求 device.ws.set 所需的 device 權限範圍，並寫明這三個事件的名稱。device.key 是高頻率事件，"*" 不會比對到它，所以必須寫明。

{"jsonrpc":"2.0","id":1,"method":"session.hello","params":{
  "client":{"name":"Example window switcher","version":"1"},
  "scopes":["device","observe"],
  "subscribe":["device.ws","device.key","device.link"],
  "snapshot":false
}}

頁面有變化時就傳送整個頁面。回覆為 {"rev":…}。

{"jsonrpc":"2.0","id":2,"method":"device.ws.set","params":{
  "active":2,"count":4,"sel":0,
  "windows":[
    {"tone":"blue","title":"kitty — claude · header refactor"},
    {"title":"firefox — github · pulls"}
  ]
}}
  • count：要繪製幾個工作區標籤，0 到 9。
  • active：目前工作區的標籤，從 1 開始，最大為 count；沒有目前工作區時為 0。
  • windows：最多六列，依裝置列出的順序。title 在裝置上會截斷為 48 個 UTF-8 位元組，以「…」結尾。tone 為 blue、amber、green、red 或 gray；未設定時該列為灰色。
  • sel：醒目顯示的列，從 0 開始，小於列數；沒有列時為 0。

超出範圍的值會以 -32009 拒絕，並由 data.field 指出欄位；缺少欄位或型別錯誤則回傳 -32602。服務會保留你最後傳送的頁面，並在 Omarchy 頁面顯示時呈現它，包括裝置重新連線之後。服務本身重新啟動後不會保留，所以每次連線時都要重新傳送頁面。這個頁面必須在裝置的頁面清單上。使用者可以從裝置本身的頁面管理加入它，或由擁有 device 權限範圍的用戶端透過 device.faces.set 傳送整份頁面清單，其中包含一個 omarchy 項目。服務只接受裝置本身會接受的頁面清單：agents 在最前、settings 在最後，兩者都不能出現在中間；最多八個頁面，每個都有自己從 1 到 8 的 id；最多三個 macropad 與一個 timer；每個頁面都要有名稱。其他清單都會以 -32009 拒絕，由 data.why 指出違反的規則，且不會傳送任何東西。Mac 應用程式的「頁面與按鍵」頁面不提供此頁面。

在頁面上點按會以 device.ws 送達，帶有 go（標籤對應的工作區編號）或 win（你上次傳送的視窗中從 0 開始的列號）：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"device.ws","rev":130,"data":{"win":1}
}}

Omarchy 頁面顯示時，裝置的按鍵以 device.key 送達：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"device.key","rev":131,"data":{"k":"cw","act":2,"shift":false,"f":2}
}}
  • k：enter、cancel、left、right，或滾輪的 cw 與 ccw。
  • act：1 為按下，0 為放開，2 為滾輪的一格。
  • shift：是否按住 SHIFT。放開事件帶有其按下時的 shift 與 f。SHIFT 與 PTT 本身從不作為按鍵送達。
  • f：按下按鍵時所在頁面的 id。

裝置的連線狀態以 device.link 送達，在連線或其工作階段變化時傳送：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"device.link","rev":132,
  "data":{"link":"connected","session":"live","host_online":true,
    "sid":314159,"fw":"0.13.1","boot":false}
}}

link 為 connected、degraded 或 offline；session 為 absent、linked、await_hello、syncing、live 或 degraded；裝置認為這台電腦在線時，host_online 為 true。裝置的韌體版本 fw 與 boot 在未知時為 null。服務關閉時送出的事件只帶有 link、session 與 host_online。用這個事件顯示裝置是否在線；裝置連線時不需要重新傳送頁面。

沒有裝置時，服務會進入靜止狀態。連續十分鐘沒有裝置連線時，它會停止從助理工作階段收集資料：停止輪詢 Claude Code 與 Codex、停止監看對話記錄與讀取用量，並在裝置連線的那一刻重新開始。它會以 service.dormancy 告知這件事，"*" 會包含此事件；同一個物件也在 snapshot.service.dormancy 中，service.info 則帶有 collecting 與 dormant_since：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"service.dormancy","rev":140,
  "data":{"window_s":600,"collecting":false,"dormant_since":"2026-11-11T01:51:00.000Z"}
}}

dormant_since 在收集期間以及從未連線過裝置時為 null；不需要等待裝置而啟動的服務會為整個物件傳送 null。靜止期間，你的連線、你的助理與你呼叫的每個方法都照常運作。如果你的應用程式也會從自己的工作階段收集資料，請比照辦理：在 device.link 顯示沒有裝置十分鐘後，Omarchy 橋接會停止為頁面提供資料並停止查看它的工作階段，裝置連線後再重新開始。

整合檢查清單

發布之前，請測試：在兩個螢幕上的第一次聊天與後續訊息；被後端拒絕、並以 agent.order.result 回報的指令；配套程式轉寫及其本機備援（如果你有提供）；有其他應用程式時的溢出；登出與重新連線；串流訊息的取代；對過期提問的按鍵；多選分頁；取消與送出；後端送出失敗；唯讀設定；思考強度目錄不同的模型切換；以及過期的設定確認。

可執行的範例還會在 tools/tests/test_native_companion.py 中以模擬後端進行檢查。公開的請求結構描述與方法權限來自 deckd api-doc。請讓這些介面與特定服務供應商的掛鉤保持分離，這樣自訂助理就不需要韌體分支或 Conol 帳號。
