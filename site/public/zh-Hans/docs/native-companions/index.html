原生配套程序 API

适用于任何助手的原生集成

为任何助手构建原生配套程序。你的应用掌管自己的对话和模型连接；OpenWalkieTalkie 提供分组的设备列表、语音输入、对话显示、提问和会话设置。Conol 使用的就是这同一个公开接口。

需要 0.11.0 或更新版本的 OpenWalkieTalkie 应用、服务和固件。这是一个基于 JSON-RPC 的本地桌面集成，不依赖 Conol。现有的 CLI 钩子仍然受支持。

试用示例

启动 OpenWalkieTalkie，连接设备，下载示例，然后运行：

python3 native_companion.py

Python 3.10+ 即可，不需要任何包或凭据。选择 Example → + New chat，口述第一条消息，新对话就会在设备上打开。说“form”可以试用分页的单选题、多选、口述文字和最后的确认。打开会话设置，可以在两个脚本化的演示模型及其思考强度选项之间切换。示例不会调用任何模型 API。按 Ctrl-C 会释放它的注册。

示例中的 Companion.order、Companion.apply_settings 和表单提交分支，就是接入你的后端的地方。它在内存中保存一小段对话记录和表单草稿；正式的应用应当从自己的对话存储中恢复这些内容。一次只运行一个演示，因为两份副本都使用“Example”设备标题。

连接与发现

从你的桌面进程连接到同一用户的 Unix 域套接字。每行发送一个 UTF-8 JSON-RPC 2.0 对象，每个请求使用不同的 id。按 id 对应回复；通知可能夹在回复之间到达。后端工作进行期间保持心跳。

  • 自定义位置：设置了该变量时为 $DECKD_DATA_DIR/deckd.sock。
  • macOS：~/Library/Application Support/OpenWalkieTalkie/deckd.sock。
  • Linux：${XDG_DATA_HOME:-~/.local/share}/openwalkietalkie/deckd.sock，也就是 Omarchy 安装运行服务所用的文件夹。Linux 是服务、Omarchy 桥接和配套应用都支持的平台（见 Omarchy 指南）。

每次连接都以此开始：

{"jsonrpc":"2.0","id":1,"method":"session.hello","params":{
  "client":{"name":"Example companion","version":"1"},
  "scopes":["agent","observe"],
  "subscribe":["agent.order","agent.answer","focus.changed","session.settings_requested"],
  "snapshot":false
}}

套接字会验证本地操作系统用户。这个集成只请求 agent 和 observe。你拥有的事件包含处理你的对话所需的内容；这些权限范围不会让你读取其他应用的私有对话记录。不需要向守护进程发送任何远程 API 密钥。请把套接字留在受信任的桌面进程中，不要把原始 RPC 桥接暴露给网页内容。

套接字不存在表示服务不可用：显示未连接状态，并以退避方式重试。如果两个新方法中任何一个返回 -32601，说明守护进程不支持原生配套程序；请提示用户更新，而不是悄悄报告集成已连接。各个方法、它们的权限范围和请求模式都在 API 参考中。

套接字是已连接应用的唯一入口。服务在 127.0.0.1 上的 HTTP 和 WebSocket 入口，以及打开它的持有者令牌，默认都是关闭的。只有当旧版 OpenWalkieTalkie 安装留下的 Claude Code HTTP 钩子仍需要它时，服务才会保持这个入口开启；config.toml 中明确的 [api] tcp 设置始终优先。下一个版本计划移除这个入口及其令牌。不要基于它们开发。

注册会话并分组

每个对话注册一个助手，另外可以注册一个启动器。为每个应用/账户/对话保留一个稳定的、带命名空间的 key。在所属连接上，同一个 key 的注册是幂等的。

{"jsonrpc":"2.0","id":2,"method":"agent.register","params":{
  "kind":"other","name":"Plan the release","key":"example:personal:chat-42",
  "caps":{"answer":"push","order":"push","focus":true},"lease_ttl_s":30
}}

保存返回的 agent ID，后续请求都要用到它。下面的示例用 ag_example 作为占位符。

{"jsonrpc":"2.0","id":3,"method":"agent.companion.set","params":{
  "agent":"ag_example","profile":{
    "app_id":"org.example.companion","group_id":"personal",
    "group_label":"Example","role":"session"
  }
}}

app_id 是稳定的应用标识符（1–64 个 ASCII 字母、数字、点、短横线或下划线）。group_id 标识应用中的一个账户或工作区（1–128 个 UTF-8 字节）。group_label 是它显示的标题（1–24 个 UTF-8 字节）。标签和 ID 不能为空，也不能包含控制字符。这些是公开的显示字段：请使用不透明的账户 ID，而不是凭据或私人账户名。对于应当在设备上分成不同页的分组，请使用不同的标签，例如“Example · Work”：固件按显示的标签分组；桌面端的分组和溢出提升则使用应用/账户 ID。

role 是 session 或 launcher。profile: null 会移除原生的显示方式。在 API 中 kind 仍表示服务提供商身份；自定义助手请用 other。现有的服务提供商类型也接受配套程序配置。Conol 可选的机器人图案来自它的 kind；其他应用集成时既不需要这个图案，也不需要新的固件枚举值。

原生焦点通过事件发给你的应用，而不是向终端注入输入。共有八个共享的物理槽位。请检查返回的 slot（null 表示溢出）。聚焦一个溢出的配套程序时，先按正常方式分配槽位；如果所有槽位都被占用，它可以替换同一所属连接、同一应用和同一分组中一个未固定的会话。这种回退会保留启动器、其他账户和其他应用。当所有候选都受保护时，它不保证能拿到槽位。不要注册没有上限的历史：发布一个有用的活动窗口，完整列表保存在你自己的应用里。

每 10 秒发送一次带有你所拥有助手 ID 的 agent.heartbeat，以维持 30 秒的租约。退出登录或关闭时，使用 agent.release。套接字断开后，重新连接并重新注册。如果注册返回所有权冲突 -32004，agent.claim {"key":"…"} 可以收回孤立或已过期的注册；它不能接管仍处于活动状态的连接。重新连接后，请重新发布配置、设置、对话记录和当前的提问。租约和守护进程都不是你的持久聊天数据库。

开始并激活新聊天

注册一个名为 + New chat 的启动器，使用 role: "launcher"，并与它的对话使用同一个分组。它的指令能力必须是 push。角色控制显示方式和槽位保护；它不会替你创建后端会话。

按以下格式处理通知：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"agent.order","rev":123,
  "data":{"agent":"ag_launcher","text":"Help me plan the release","order":"or_12"}
}}
  1. 把 data.agent 解析为你拥有的账户和启动器。在这个连接内，用通知的 rev 和 type 去重。
  2. 通过你经过身份验证的后端创建对话和第一条用户消息。保存它的持久 ID；对同一个启动器的并发创建要串行处理。
  3. 用新对话自己的稳定 key 和 role: "session" 注册它。发布实际的设置和最近的消息。
  4. 在你的应用中选中新对话，然后调用 agent.focus {"agent":"ag_new"}。守护进程会在聚焦前发送槽位替换的更新，固件会在松开 PTT 后打开该对话。已经打开的提问卡片保持不动。

处理带有 data.source: "device" 的 focus.changed 时，在你的应用中选中对应的对话，或者为启动器打开一个空白的输入框。不要再回一个聚焦请求，以免形成反馈循环。未知助手 ID 的事件必须忽略。

永远不要盲目重试结果不确定的后端创建。请使用后端的幂等键，或先核对持久化的结果。套接字重新连接并不能证明之前的创建失败了。示例中的本地内存创建只是演示；正式的后端必须提供这种保证。

保持两边的对话记录同步

对于已有的会话，agent.order 表示向该对话发送一条后续消息。在后端使用稳定的客户端消息 ID，更新应用中可见的对话记录，并恢复它的响应流。只同步到设备会让你的桌面界面过时。

每条为你的助手口述或输入的指令，都在 data.order 中带有一个指令 ID；在你的某张完成卡片上选择的步骤（ctx: "step"）不带 ID，也不需要报告。如果消息无法送达你的对话，请报告它，设备就会显示该指令未送达：

{"jsonrpc":"2.0","id":5,"method":"agent.order.result","params":{
  "agent":"ag_example","order":"or_12","ok":false,"reason":"backend_refused"
}}

reason 是一个由小写字母、数字和下划线组成的词，最多 32 字节。每条指令最多报告一次，且须在十分钟内；ok: true 会被接受，但不改变任何东西。回复是 {rev, shown}，其中 shown 为 card、toast 或 none。守护进程因此放到你的助手上的卡片，会以带有 host: "failure" 的 card.set 送达；你的下一次 agent.card.set 会替换它。如果它取代了你的一张信息卡片（没有任何东西在等待的卡片），对那张卡片的 agent.card.clear 仍会得到 {rev} 回复，而失败卡片保持不变。较旧的守护进程不发送 order，并回复 -32601：这时跳过报告即可。当该方法存在时，service.info 会在 capabilities 中列出 order.result。

用稳定的 ID 发布公开的用户消息和助手消息：

{"jsonrpc":"2.0","id":4,"method":"agent.reply","params":{
  "agent":"ag_example","text":"I can help with the release.","speak":false,
  "message":{"id":"message-42","role":"assistant","streaming":true}
}}

流式输出时，用同一个消息 ID 发送即可替换文字；最后以 streaming: false 结束。用户消息也要用 role: "user" 发送。守护进程为每个助手最多保留 64 条消息和 512 KiB；请发布一个有上限的近期窗口。不要把私有的推理过程、凭据和内部工具参数放进同步的对话记录。朗读需要通过 speak 主动开启。

用 agent.update 设置对话名称、短标题和 state（working、question、ready、error 或 idle）。保持后端的实际状态，并如实显示发送失败，不要声称消息已被接受。一次回复结束时，先发布它的最终消息（streaming: false），再设置 state: ready：状态变为 ready 时，设备会朗读已有的回复，但绝不会朗读对话上一次变为 working 之前发布的回复。

原生配套程序还可以通过 agent.reply 发布公开的工具活动：使用 message.role: "tool"，明确的 activity（running、completed、failed 或 stopped），以及 summary: {"label":"Running a command","detail":"cargo test"}。这个可选的摘要需要模式中包含 ActivitySummary 的新版守护进程；0.11.0 固件可以显示由此产生的行。请使用稳定的调用 ID，只在运行期间设置 streaming，并在上一个调用消失时将其结束或停止。只发送可见的标签和预览，完整的工具输入/结果留在所属应用中，并保持 speak: false。摘要内容和对话文字一样，按内容权限范围进行隐去。

用你自己的语音模型转写

如果你的应用有自己的语音识别器，请用 caps.transcribe: "push" 注册。之后守护进程会录下每一次发给该助手的按键说话，并在用户松开 PTT 时提供给你的连接。你给出的文字会成为这次按键的最终转写，因此设备上的转写、agent.order 和口述的 agent.answer 都会使用它。守护进程自己的识别器仍会同时运行；如果你失败、拒绝、发送空文本、断开连接或超过 20 秒，就由它提供最终转写。按住期间不会显示它识别出的文字，因为那不是最终要发送的内容。设备会改为显示随麦克风音量变化的 RECORDING 波形（需要新版固件；旧版固件显示空白的转写）。旧版守护进程会忽略这个字段。如果需要事先知道，请检查 service.info 的 capabilities 中是否有 transcribe.companion。

{"jsonrpc":"2.0","method":"event","params":{
  "type":"agent.transcribe","rev":124,
  "data":{"agent":"ag_example","transcription":"tr_7","mime":"audio/wav",
    "rate":16000,"ms":4200,"bytes":134444,"page":98304,"locale":"en-US"}
}}

录音为 16 kHz、16 位单声道 WAV，最长约一分钟。用 agent.transcribe.audio {"transcription":"tr_7","offset":0} 分页获取，它返回 {offset,total,data}，其中 data 为 base64。按解码后的长度推进 offset，直到达到 total。然后用 agent.transcribe.result {"transcription":"tr_7","text":"…"} 回复且只回复一次；如果无法转写，则用 "error":"…" 回复。出错时请立即回复，不要保持沉默，这样设备就不必等到时限用完。只有所属连接可以读取或回复这一请求。请求只发给该连接，从不出现在事件总线上。点名设备本身的按键说话，以及短于 0.3 秒的按键，永远不会被提供。只有在 [voice.stt] companion 开启时（默认开启），音频才会离开守护进程，用户可以关闭它。

在设备上处理复杂提问

公开的提问原语是 agent.card.set。一张卡片最多有四个选项，并可选地允许自由文本。请在你的应用中构建多步表单；每显示一个步骤都使用新的卡片 ID。

{"jsonrpc":"2.0","id":5,"method":"agent.card.set","params":{
  "agent":"ag_example","type":"q","text":"1/3 Choose a language",
  "choices":[{"label":"Python"},{"label":"Rust"},{"label":"More"},{"label":"Cancel"}],
  "free_text":false,"deliver":"push","origin":{"kind":"custom"}
}}

保存 result.card.id。只有当 data.agent 和 data.card 都与当前提问一致时，才接受 agent.answer。data.choice 是从零开始的选项索引；data.text 带有口述的自由文本。永远不要把迟到的回答用到替换后的提问上。发布下一步之前，用 agent.card.clear {"agent":"…","card":17,"delivered":false} 清除上一张卡片。

  • 选项列表太长时分页显示，而不是截断。把按键留给导航。
  • 多选用切换来实现，翻页时保留已选项，直到 Next。
  • 输入/口述的回答或“其他”选项，使用专门的 free_text: true 步骤。
  • 草稿保存在本地。用 Submit、Edit 和 Cancel 确认完整的回答。
  • 只有 Submit 会把回答发给后端中那个正在等待的工具调用或批准。导航、编辑和取消都不能批准任何东西。
  • 只有在后端接受提交后才确认送达。失败时保留草稿，并在明确重试时复用同一个稳定的提交 ID。重新连接后，再次确认后端的提问仍在等待中。

如果表单无法在设备的限制内表示，请提供一个明确的“在应用中打开”选项。应用应当聚焦到相关的提问，而不是假装表单已经完成。示例用一个脚本化的本地表单演示这个向导；Conol 把同样的模式接到了 AskUser 和工作流批准上。

显示并更改模型 / 思考强度

用 agent.session.set 为你拥有的任何助手报告设置。只显示的设置不需要目录：

{"jsonrpc":"2.0","id":6,"method":"agent.session.set","params":{
  "agent":"ag_example","controls":{
    "model":"My model","effort":"High","editable":false,
    "note":"Change these settings in Example."
  }
}}

对于可在设备上编辑的设置，请提供稳定的模型 ID、易读的标签，以及每个模型支持的思考强度值。发送后端实际的选择，而不是猜测的默认值。

{"jsonrpc":"2.0","id":7,"method":"agent.session.set","params":{
  "agent":"ag_example","controls":{
    "model":"fast","effort":"low","editable":true,"note":"",
    "models":[
      {"id":"fast","label":"Fast model","efforts":["low","high"],"default_effort":"low"},
      {"id":"simple","label":"Simple model","efforts":[],"default_effort":""}
    ]
  }
}}

model 以及每个模型的 ID/标签，最长 128 个 UTF-8 字节；思考强度字符串最长 32；note 最长 256。最多 64 个模型，每个模型最多 16 个思考强度，模型 ID 和思考强度值都必须唯一。控制字符会被拒绝。可编辑的选择必须属于它的目录；空的思考强度表示后端默认值或没有思考强度设置。非空的 default_effort 必须列在该模型的思考强度中。

在设备上选择会发出 session.settings_requested（requested 前是下划线）：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"session.settings_requested","rev":124,
  "data":{"agent":"ag_example","model":"fast","effort":"high","request_rev":19}
}}

在后端应用所请求的设置，然后调用 agent.session.set，带上实际得到的控件和 request_rev: 19。使用 data.request_rev，而不是外层事件的 rev。设备会让现有的选择保持待定，直到收到确认。失败时，用一条简短说明的 note 确认未改变的实际设置。

普通刷新不带 request_rev，也不会了结待定的请求。不匹配、重复或过期的确认会被拒绝。待定的更改在 45 秒后超时。在异步处理中保持请求与助手的对应关系，如果响应丢失，请与后端核对。守护进程验证传输和所有权；授权并应用模型更改仍是你的应用的责任。

为 Omarchy 页面提供数据

设备的 Omarchy 页面是一个窗口切换器：一行最多九个工作区标签，以及最多六行窗口。其中没有任何东西是 Omarchy 专用的。任何应用都可以用 device.ws.set 填充它，并通过三个事件响应用户在那里的操作。Omarchy 桥接（源代码仓库中的 host/omarchy/）是参考客户端，CI 会在每个拉取请求上运行它的测试。

页面数据是一个公开接口，从现在起只增不减。device.ws.set 以及 device.ws、device.key 和 device.link 事件可能会增加字段；它们现有的字段都不会被重命名、改变类型或移除。请忽略你不认识的字段。

请求 device.ws.set 所需的 device 权限范围，并列出这三个事件的名称。device.key 是高频事件，"*" 不会匹配它，所以必须写明。

{"jsonrpc":"2.0","id":1,"method":"session.hello","params":{
  "client":{"name":"Example window switcher","version":"1"},
  "scopes":["device","observe"],
  "subscribe":["device.ws","device.key","device.link"],
  "snapshot":false
}}

页面有变化时就发送整个页面。回复是 {"rev":…}。

{"jsonrpc":"2.0","id":2,"method":"device.ws.set","params":{
  "active":2,"count":4,"sel":0,
  "windows":[
    {"tone":"blue","title":"kitty — claude · header refactor"},
    {"title":"firefox — github · pulls"}
  ]
}}
  • count：要绘制多少个工作区标签，0 到 9。
  • active：当前工作区的标签，从 1 开始，最大为 count；没有当前工作区时为 0。
  • windows：最多六行，按设备列出的顺序。title 在设备上会被截断到 48 个 UTF-8 字节，以“…”结尾。tone 为 blue、amber、green、red 或 gray；没有时该行为灰色。
  • sel：高亮的行，从 0 开始，小于行数；没有行时为 0。

超出范围的值会被以 -32009 拒绝，data.field 指出是哪个字段；缺少字段或类型错误则返回 -32602。服务会保留你最后发送的页面，并在 Omarchy 页面显示时展示它，包括设备重新连接之后。服务自身重启后不会保留，所以每次连接时都要重新发送页面。这个页面必须在设备的页面列表中。用户可以在设备自己的页面管理中添加它，或者由拥有 device 权限范围的客户端通过 device.faces.set 发送整个页面列表，其中包含一个 omarchy 条目。服务只接受设备本身会接受的页面列表：agents 在最前、settings 在最后，两者都不能出现在中间；最多八个页面，每个都有自己从 1 到 8 的 id；最多三个 macropad 和一个 timer；每个页面都要有名称。其他列表都会被以 -32009 拒绝，data.why 指出违反的规则，并且什么都不会发送。Mac 应用的“页面与按键”页面不提供这一页面。

在页面上点按会以 device.ws 送达，带有 go（标签对应的工作区编号）或 win（你上次发送的窗口中从 0 开始的行号）：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"device.ws","rev":130,"data":{"win":1}
}}

Omarchy 页面显示时，设备的按键以 device.key 送达：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"device.key","rev":131,"data":{"k":"cw","act":2,"shift":false,"f":2}
}}
  • k：enter、cancel、left、right，或滚轮的 cw 和 ccw。
  • act：1 为按下，0 为松开，2 为滚轮的一格。
  • shift：是否按住了 SHIFT。松开事件带有其按下时的 shift 和 f。SHIFT 和 PTT 本身从不作为按键送达。
  • f：按下按键时所在页面的 id。

设备的连接状态以 device.link 送达，在连接或其会话变化时发送：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"device.link","rev":132,
  "data":{"link":"connected","session":"live","host_online":true,
    "sid":314159,"fw":"0.13.1","boot":false}
}}

link 为 connected、degraded 或 offline；session 为 absent、linked、await_hello、syncing、live 或 degraded；设备认为这台电脑在线时 host_online 为 true。设备的固件版本 fw 和 boot 在未知时为 null。服务关闭时发出的事件只带有 link、session 和 host_online。用这个事件显示设备是否在线；设备连接时不需要重新发送页面。

没有设备时服务会进入静默。连续十分钟没有设备连接时，它会停止从助手会话收集数据：停止轮询 Claude Code 和 Codex、停止监视对话记录和读取用量，并在设备连接的那一刻重新开始。它会用 service.dormancy 告知这一点，"*" 包含该事件；同样的对象也在 snapshot.service.dormancy 中，service.info 则带有 collecting 和 dormant_since：

{"jsonrpc":"2.0","method":"event","params":{
  "type":"service.dormancy","rev":140,
  "data":{"window_s":600,"collecting":false,"dormant_since":"2026-11-11T01:51:00.000Z"}
}}

dormant_since 在收集期间以及从未连接过设备时为 null；不需要等待设备而启动的服务会为整个对象发送 null。静默期间，你的连接、你的助手和你调用的每个方法都照常工作。如果你的应用也会从自己的会话收集数据，请同样处理：在 device.link 显示没有设备十分钟后，Omarchy 桥接会停止为页面提供数据并停止查看它的会话，设备连接后再重新开始。
