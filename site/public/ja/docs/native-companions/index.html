ネイティブコンパニオン API

あらゆるエージェントのためのネイティブ連携

あらゆるエージェントのためのネイティブコンパニオンを作れます。会話とモデルへの接続はあなたのアプリが持ち、OpenWalkieTalkie はグループ化されたデバイスの一覧、音声入力、会話の表示、質問、セッションの設定を提供します。Conol もこの同じ公開インターフェースを使っています。

OpenWalkieTalkie のアプリ、サービス、ファームウェアの 0.11.0 以降が必要です。JSON-RPC によるローカルのデスクトップ連携で、Conol には依存しません。既存の CLI フックも引き続き使えます。

サンプルを試す

OpenWalkieTalkie を起動してデバイスを接続し、サンプルをダウンロードして、次を実行します。

python3 native_companion.py

Python 3.10 以降があれば十分で、パッケージや認証情報は不要です。Example → + New chat を選んで最初のメッセージを口述すると、新しい会話がデバイスで開きます。「form」と話すと、ページ送りのある単一選択の質問、複数選択、口述のテキスト、最後の確認を試せます。セッションの設定を開くと、用意された 2 つのデモ用モデルとその思考の深さの選択肢を切り替えられます。サンプルはモデルの API を呼び出しません。Ctrl-C で登録を解除します。

サンプルの Companion.order、Companion.apply_settings、フォーム送信の分岐が、あなたのバックエンドをつなぐ場所です。サンプルは短い会話履歴とフォームの下書きをメモリーに持ちますが、実際のアプリでは自身の会話の保存先から復元してください。2 つのコピーはどちらも「Example」というデバイス上の見出しを使うため、デモは一度に 1 つだけ実行します。

接続と検出

デスクトップのプロセスから、同じユーザーの Unix ドメインソケットに接続します。1 行に 1 つの UTF-8 の JSON-RPC 2.0 オブジェクトを送り、リクエストごとに別の id を使います。返信は id で対応づけます。通知は返信の合間に届くことがあります。バックエンドの処理中もハートビートを送り続けてください。

  • 上書き：変数が設定されていれば $DECKD_DATA_DIR/deckd.sock。
  • macOS：~/Library/Application Support/OpenWalkieTalkie/deckd.sock。
  • Linux：${XDG_DATA_HOME:-~/.local/share}/openwalkietalkie/deckd.sock。Omarchy のセットアップがサービスを動かすフォルダーです。Linux はサービス、Omarchy ブリッジ、コンパニオンアプリの対応プラットフォームです（Omarchy のガイド）。

接続のたびに、まず次を送ります。

{"jsonrpc":"2.0","id":1,"method":"session.hello","params":{
  "client":{"name":"Example companion","version":"1"},
  "scopes":["agent","observe"],
  "subscribe":["agent.order","agent.answer","focus.changed","session.settings_requested"],
  "snapshot":false
}}

ソケットはローカルの OS ユーザーを認証します。この連携では agent と observe だけを要求してください。自分が所有するイベントには会話の処理に必要な内容が含まれますが、これらのスコープでほかのアプリの非公開の会話履歴を読むことはできません。リモートの API キーをデーモンに送る必要はありません。ソケットは信頼できるデスクトップのプロセス内に置き、生の RPC ブリッジをウェブのコンテンツに公開しないでください。

ソケットがないのはサービスが利用できないということです。未接続と表示し、間隔を空けながら再試行してください。2 つの新しいメソッドのどちらかが -32601 を返したら、デーモンがネイティブコンパニオンに対応していません。連携できたと黙って表示するのではなく、更新を勧めてください。メソッド、スコープ、リクエストのスキーマは API リファレンスにあります。

接続アプリの入り口はソケットだけです。127.0.0.1 にあるサービスの HTTP と WebSocket の入り口と、それを開くベアラートークンは、既定でオフです。古い OpenWalkieTalkie のインストールが残した Claude Code の HTTP フックがまだ必要とする間だけ、サービスはこの入り口を開いておきます。config.toml の明示的な [api] tcp 設定は常に優先されます。入り口とトークンは次のリリースで削除する予定です。これらを前提に作らないでください。

セッションを登録してグループにまとめる

会話ごとにエージェントを 1 つ登録し、必要ならランチャーも 1 つ登録します。アプリ／アカウント／会話ごとに、安定した名前空間付きの key を使ってください。所有する接続上では、同じ key の登録はべき等です。

{"jsonrpc":"2.0","id":2,"method":"agent.register","params":{
  "kind":"other","name":"Plan the release","key":"example:personal:chat-42",
  "caps":{"answer":"push","order":"push","focus":true},"lease_ttl_s":30
}}

返された agent の ID を保存し、以降のリクエストで使います。以下の例では ag_example をプレースホルダーとして使います。

{"jsonrpc":"2.0","id":3,"method":"agent.companion.set","params":{
  "agent":"ag_example","profile":{
    "app_id":"org.example.companion","group_id":"personal",
    "group_label":"Example","role":"session"
  }
}}

app_id は安定したアプリの識別子です（ASCII の英字、数字、ドット、ハイフン、アンダースコアで 1〜64 文字）。group_id はアプリ内のアカウントまたはワークスペースを表します（1〜128 UTF-8 バイト）。group_label はその表示上の見出しです（1〜24 UTF-8 バイト）。ラベルと ID は空にできず、制御文字も使えません。これらは公開の表示用フィールドです。認証情報や非公開のアカウント名ではなく、意味を持たないアカウント ID を使ってください。デバイスで別のページに分けたいグループには、「Example · Work」のように別のラベルを付けます。ファームウェアは表示ラベルでグループ化し、デスクトップ側のグループ化とあふれた分の繰り上げはアプリ／アカウントの ID を使います。

role は session か launcher です。profile: null でネイティブの表示を取り除きます。API では kind は引き続きプロバイダーの種別を表します。独自のエージェントには other を使ってください。既存のプロバイダーの種別でもコンパニオンのプロファイルを使えます。Conol の任意のロボットの絵柄はその kind から決まります。ほかのアプリが連携するのに、その絵柄も新しいファームウェアの列挙値も必要ありません。

ネイティブのフォーカスは、ターミナルへの入力ではなくイベントであなたのアプリに届きます。共有の物理スロットは 8 つです。返された slot を確認してください（null はあふれを意味します）。あふれたコンパニオンにフォーカスすると、まず通常どおりスロットを割り当てます。すべて埋まっている場合は、同じ所有接続・同じアプリ・同じグループの、固定されていないセッションと入れ替えることがあります。この代替動作ではランチャー、ほかのアカウント、ほかのアプリは残ります。候補がすべて保護されている場合、スロットは保証されません。際限のない履歴を登録しないでください。役に立つ範囲だけを公開し、全体の一覧は自分のアプリで保持します。

所有するエージェントの ID を付けた agent.heartbeat を 10 秒ごとに送り、30 秒のリースを保ちます。サインアウトや終了のときは agent.release を使います。ソケットが切れたら、接続し直して再び登録します。登録が所有権の競合 -32004 を返した場合、agent.claim {"key":"…"} で、所有者のいない登録や期限切れの登録を取り戻せます。動作中の接続を奪うことはできません。再接続後は、プロファイル、設定、会話履歴、現在の質問を公開し直してください。リースもデーモンも、チャットを永続的に保存するデータベースではありません。

新しいチャットを始めてアクティブにする

+ New chat という名前のランチャーを、role: "launcher" と、その会話と同じグループで登録します。指示の受け取り方は push でなければなりません。ロールは表示とスロットの保護を決めるもので、バックエンドのセッションを代わりに作るものではありません。

通知は次の形式で扱います。

{"jsonrpc":"2.0","method":"event","params":{
  "type":"agent.order","rev":123,
  "data":{"agent":"ag_launcher","text":"Help me plan the release","order":"or_12"}
}}
  1. data.agent から、所有するアカウントとランチャーを特定します。この接続の中で、通知の rev と type を使って重複を除きます。
  2. 認証済みのバックエンドで、会話と最初のユーザーメッセージを作成します。その永続的な ID を保持し、同じランチャーへの同時の作成は順番に処理します。
  3. 新しい会話を、それ自身の安定した key と role: "session" で登録します。実際の設定と最近のメッセージを公開します。
  4. アプリで新しい会話を選び、agent.focus {"agent":"ag_new"} を呼びます。デーモンはフォーカスの前にスロットの入れ替えの更新を送り、ファームウェアは PTT を離したあとにその会話を開きます。すでに開いている質問カードはそのまま残ります。

data.source: "device" を持つ focus.changed を受けたら、アプリで対応する会話を選ぶか、ランチャーなら空の入力欄を開きます。フォーカスのリクエストを送り返して、ループを作らないでください。知らないエージェント ID のイベントは無視しなければなりません。

結果のわからないバックエンドでの作成を、やみくもに再試行しないでください。バックエンドのべき等キーを使うか、先に永続化された結果と照合します。ソケットの再接続は、前の作成が失敗した証拠になりません。サンプルのローカルなメモリー上での作成は説明用です。実際のバックエンドではこの保証が必要です。

両方の会話履歴を最新に保つ

既存のセッションに対する agent.order は、その会話に続きのメッセージを届けることを意味します。バックエンドでは安定したクライアント側のメッセージ ID を使い、アプリに表示される会話履歴を更新し、応答のストリームを再開してください。デバイスにだけ反映すると、デスクトップの画面が古いままになります。

エージェントに向けて口述または入力された指示には、data.order に指示の ID が付きます。あなたの完了カードで選ばれたステップ（ctx: "step"）には付かず、報告も不要です。メッセージを会話に届けられなかったときは報告してください。デバイスに、指示が届かなかったと表示されます。

{"jsonrpc":"2.0","id":5,"method":"agent.order.result","params":{
  "agent":"ag_example","order":"or_12","ok":false,"reason":"backend_refused"
}}

reason は小文字の英字、数字、アンダースコアからなる 1 語で、最大 32 バイトです。報告は指示ごとに 1 回まで、10 分以内に行います。ok: true は受け付けられますが、何も変わりません。返信は {rev, shown} で、shown は card、toast、none のいずれかです。そのためにデーモンがあなたのエージェントに置くカードは、host: "failure" 付きの card.set として届きます。次に agent.card.set を送るとそれが置き換わります。そのカードがあなたの情報カード（何も待っていないカード）の代わりに置かれた場合、そのカードへの agent.card.clear にも {rev} が返り、失敗のカードは残ります。古いデーモンは order を送らず、-32601 を返します。その場合は報告を省略してください。このメソッドがあれば、service.info の capabilities に order.result が含まれます。

公開するユーザーとアシスタントのメッセージは、安定した ID を付けて送ります。

{"jsonrpc":"2.0","id":4,"method":"agent.reply","params":{
  "agent":"ag_example","text":"I can help with the release.","speak":false,
  "message":{"id":"message-42","role":"assistant","streaming":true}
}}

ストリーミング中は同じメッセージ ID で送るとテキストが置き換わります。最後は streaming: false で終えます。ユーザーのメッセージも role: "user" で送ってください。デーモンが保持するのはエージェントごとに最大 64 件、512 KiB までです。範囲を絞った最近の分を公開してください。非公開の推論、認証情報、内部のツール引数は反映する会話履歴に入れないでください。読み上げは speak で明示的に有効にします。

会話の名前、短いタイトル、state（working、question、ready、error、idle）は agent.update で設定します。バックエンドの実際の状態を保ち、送信の失敗は、メッセージを受け付けたかのように装わずに表示してください。応答が終わったら、state: ready を設定する前に最後のメッセージ（streaming: false）を公開します。デバイスは状態が ready になったときに手元の返信を読み上げますが、会話が最後に working になる前に公開された返信は読み上げません。

ネイティブコンパニオンは、agent.reply で公開のツールの動作も公開できます。message.role: "tool"、running、completed、failed、stopped のいずれかを明示した activity、そして summary: {"label":"Running a command","detail":"cargo test"} を使います。この任意の要約には、スキーマに ActivitySummary を持つ更新済みのデーモンが必要です。ファームウェア 0.11.0 はその結果の行を表示できます。安定した呼び出し ID を使い、streaming は実行中だけ設定し、前の呼び出しが消えたら完了または停止にしてください。送るのは表示用のラベルとプレビューだけにし、ツールの入力や結果の全体は所有するアプリに残し、speak: false のままにします。要約の内容は、会話のテキストと同じくコンテンツのスコープに応じて伏せられます。

独自の音声モデルで文字起こしする

アプリに独自の音声認識エンジンがある場合は、caps.transcribe: "push" で登録します。するとデーモンはそのエージェント宛ての押下ごとに録音し、PTT が離されたときにあなたの接続に渡します。あなたのテキストがその押下の最終的な文字起こしになり、デバイスの文字起こし、agent.order、口述の agent.answer にそれが使われます。デーモン自身の認識エンジンも並行して動き、あなたが失敗、拒否、空のテキストの送信、切断をしたとき、または 20 秒を超えたときに最終的な文字起こしを提供します。押している間はその結果を表示しません。実際に送られる内容ではないためです。代わりにデバイスはマイクの音量に合わせて動く RECORDING の波形を表示します（更新済みのファームウェアの場合。古いファームウェアでは文字起こしが空のまま表示されます）。古いデーモンはこのフィールドを無視します。事前に知る必要があれば、service.info の capabilities に transcribe.companion があるか確認してください。

{"jsonrpc":"2.0","method":"event","params":{
  "type":"agent.transcribe","rev":124,
  "data":{"agent":"ag_example","transcription":"tr_7","mime":"audio/wav",
    "rate":16000,"ms":4200,"bytes":134444,"page":98304,"locale":"en-US"}
}}

録音は 16 kHz、16 ビット、モノラルの WAV で、長さは最大で約 1 分です。agent.transcribe.audio {"transcription":"tr_7","offset":0} でページ単位に取得します。戻り値は {offset,total,data} で、data は base64 です。total に達するまで、デコードした長さだけ offset を進めます。そのあと agent.transcribe.result {"transcription":"tr_7","text":"…"} でちょうど 1 回だけ答えます。文字起こしできない場合は "error":"…" で答えます。エラーは黙っていないですぐに返してください。そうすればデバイスが制限時間まで待たずに済みます。この依頼を読んだり答えたりできるのは所有する接続だけです。依頼はその接続にだけ送られ、イベントバスには現れません。デバイス自体を指名した押下と、0.3 秒未満の押下が渡されることはありません。音声がデーモンの外に出るのは [voice.stt] companion がオンのとき（既定でオン）だけで、ユーザーはこれをオフにできます。

複雑な質問をデバイスで扱う

公開の質問の基本要素は agent.card.set です。カードには最大 4 つの選択肢と、任意で自由入力を持たせられます。複数ステップのフォームはアプリの側で組み立ててください。表示するステップごとに新しいカード ID を使います。

{"jsonrpc":"2.0","id":5,"method":"agent.card.set","params":{
  "agent":"ag_example","type":"q","text":"1/3 Choose a language",
  "choices":[{"label":"Python"},{"label":"Rust"},{"label":"More"},{"label":"Cancel"}],
  "free_text":false,"deliver":"push","origin":{"kind":"custom"}
}}

result.card.id を保存します。agent.answer を受け付けるのは、data.agent と data.card の両方が現在の質問と一致するときだけです。data.choice は 0 から始まる選択肢の番号、data.text は口述の自由入力です。遅れて届いた回答を、置き換えたあとの質問に適用してはいけません。次のステップを公開する前に、agent.card.clear {"agent":"…","card":17,"delivered":false} で前のカードを消してください。

  • 長い選択肢の一覧は切り詰めずにページに分けます。キーは移動用に残しておきます。
  • 複数選択はトグルとして実装し、Next まではページをまたいで選択を保ちます。
  • 入力・口述の回答や「その他」の選択肢には、専用の free_text: true のステップを使います。
  • 下書きはローカルに保持します。回答全体は Submit、Edit、Cancel で確認します。
  • 回答をバックエンドの待機中のツール呼び出しや承認に送るのは Submit だけです。移動、編集、キャンセルで何かを承認してはいけません。
  • 送信の完了を伝えるのは、バックエンドが受け付けてからにします。失敗したら下書きを残し、明示的な再試行では同じ安定した送信 ID を使います。再接続後は、バックエンドの質問がまだ待機中か確認し直してください。

フォームがデバイスの制限内で表せない場合は、「アプリで開く」という明示的な選択肢を用意してください。アプリは該当する質問にフォーカスし、フォームが完了したふりをしてはいけません。サンプルは用意されたローカルのフォームでこのウィザードを実演しています。Conol は同じ仕組みを AskUser とワークフローの承認につないでいます。

モデルと思考の深さを表示・変更する

所有するエージェントの設定は agent.session.set で報告します。表示だけの設定にはカタログは不要です。

{"jsonrpc":"2.0","id":6,"method":"agent.session.set","params":{
  "agent":"ag_example","controls":{
    "model":"My model","effort":"High","editable":false,
    "note":"Change these settings in Example."
  }
}}

デバイスで変更できる設定には、安定したモデル ID、読みやすいラベル、各モデルが対応する思考の深さの値を渡します。推測した既定値ではなく、バックエンドで実際に選ばれているものを送ってください。

{"jsonrpc":"2.0","id":7,"method":"agent.session.set","params":{
  "agent":"ag_example","controls":{
    "model":"fast","effort":"low","editable":true,"note":"",
    "models":[
      {"id":"fast","label":"Fast model","efforts":["low","high"],"default_effort":"low"},
      {"id":"simple","label":"Simple model","efforts":[],"default_effort":""}
    ]
  }
}}

model と各モデルの ID／ラベルは最大 128 UTF-8 バイト、思考の深さの文字列は 32、note は 256 までです。モデルは最大 64 個、1 モデルあたりの思考の深さは最大 16 個で、モデル ID と思考の深さの値はそれぞれ一意でなければなりません。制御文字は拒否されます。変更可能な選択はそのカタログに含まれていなければなりません。空の思考の深さは、バックエンドの既定値か、思考の深さの設定がないことを表します。空でない default_effort は、そのモデルの思考の深さに含まれていなければなりません。

デバイスで選ぶと session.settings_requested が発行されます（requested の前はアンダースコアです）。

{"jsonrpc":"2.0","method":"event","params":{
  "type":"session.settings_requested","rev":124,
  "data":{"agent":"ag_example","model":"fast","effort":"high","request_rev":19}
}}

要求された設定をバックエンドに適用してから、実際に適用された結果のコントロールと request_rev: 19 を付けて agent.session.set を呼びます。外側のイベントの rev ではなく data.request_rev を使ってください。デバイスは確認が届くまで、既存の選択を保留にしておきます。失敗したときは、短い説明の note を付けて、変わっていない実際の設定を確定させます。

通常の更新は request_rev を付けず、保留中の要求を確定させません。一致しない、重複した、期限切れの確認は拒否されます。保留中の変更は 45 秒でタイムアウトします。非同期の処理でも要求とエージェントの対応を保ち、応答が失われたらバックエンドと照合してください。デーモンが検証するのは通信と所有権です。モデルの変更を許可し適用する責任はアプリにあります。

Omarchy のページにデータを送る

デバイスの Omarchy のページはウィンドウの切り替え画面です。最大 9 個のワークスペースのチップが並ぶ行と、最大 6 行のウィンドウがあります。Omarchy に固有のものは何もありません。どのアプリでも device.ws.set で内容を埋め、そこでのユーザーの操作に 3 つのイベントで応えられます。Omarchy ブリッジ（ソースリポジトリの host/omarchy/）が参照クライアントで、CI がプルリクエストのたびにそのテストを実行します。

ページへのデータ送信は公開インターフェースで、今後は追加のみです。device.ws.set と、device.ws、device.key、device.link のイベントにはフィールドが増えることがありますが、既存のフィールドの名前の変更、型の変更、削除はありません。知らないフィールドは無視してください。

device.ws.set に必要な device スコープを要求し、3 つのイベントを名前で指定します。device.key は頻度の高いイベントで、"*" には一致しないため、名前で指定する必要があります。

{"jsonrpc":"2.0","id":1,"method":"session.hello","params":{
  "client":{"name":"Example window switcher","version":"1"},
  "scopes":["device","observe"],
  "subscribe":["device.ws","device.key","device.link"],
  "snapshot":false
}}

ページが変わるたびにページ全体を送ります。返信は {"rev":…} です。

{"jsonrpc":"2.0","id":2,"method":"device.ws.set","params":{
  "active":2,"count":4,"sel":0,
  "windows":[
    {"tone":"blue","title":"kitty — claude · header refactor"},
    {"title":"firefox — github · pulls"}
  ]
}}
  • count：表示するワークスペースのチップの数。0〜9。
  • active：現在のワークスペースのチップ。1 から始まり、最大 count。どれも現在のものでなければ 0。
  • windows：最大 6 行。デバイスが並べる順番です。title はデバイス上で 48 UTF-8 バイトに切り詰められ、末尾に「…」が付きます。tone は blue、amber、green、red、gray のいずれかで、指定がなければ灰色です。
  • sel：ハイライトする行。0 から始まり、行数未満。行がなければ 0。

範囲外の値は -32009 で拒否され、data.field がそのフィールドを示します。フィールドの欠落や型の誤りは -32602 になります。サービスは最後に送られたページを保持し、Omarchy のページが表示されているときに、デバイスが接続し直したあとも含めて表示します。サービス自身の再起動後は保持しないため、接続するたびにページを送り直してください。このページはデバイスのページ一覧に入っていなければなりません。ユーザーがデバイス自身のページ管理から追加するか、device スコープを持つクライアントが omarchy の項目を含むページ一覧全体を device.faces.set で送ります。サービスが受け付けるのは、デバイス自身が受け付ける一覧だけです。agents が最初、settings が最後で、どちらも途中には置けません。ページは最大 8 個で、それぞれ 1〜8 の固有の id を持ち、macropad は最大 3 個、timer は 1 個まで、すべてのページに名前が必要です。それ以外は -32009 で拒否され、data.why が違反した規則を示し、何も送られません。Mac アプリの「ページとキー」ページでは追加できません。

ページをタップすると device.ws が届きます。go（チップのワークスペース番号）か、win（最後に送ったウィンドウのうち 0 から数えた行）のどちらかを持ちます。

{"jsonrpc":"2.0","method":"event","params":{
  "type":"device.ws","rev":130,"data":{"win":1}
}}

Omarchy のページが表示されている間、デバイスのキーは device.key として届きます。

{"jsonrpc":"2.0","method":"event","params":{
  "type":"device.key","rev":131,"data":{"k":"cw","act":2,"shift":false,"f":2}
}}
  • k：enter、cancel、left、right、またはホイールの cw と ccw。
  • act：1 は押下、0 は離した、2 はホイールの 1 段。
  • shift：SHIFT を押していたかどうか。離したイベントは、押したときの shift と f を持ちます。SHIFT と PTT がそれ自体のキーとして届くことはありません。
  • f：キーが押されたページの id。

デバイスの接続状態は、接続またはそのセッションが変わるたびに device.link として届きます。

{"jsonrpc":"2.0","method":"event","params":{
  "type":"device.link","rev":132,
  "data":{"link":"connected","session":"live","host_online":true,
    "sid":314159,"fw":"0.13.1","boot":false}
}}

link は connected、degraded、offline のいずれか、session は absent、linked、await_hello、syncing、live、degraded のいずれかです。host_online は、デバイスがこのパソコンを接続中とみなしている間 true です。デバイスのファームウェアのバージョン fw と boot は、不明な間は null です。サービスが終了するときに送るイベントには link、session、host_online だけが含まれます。このイベントでデバイスがあるかどうかを表示してください。接続したときにページを送り直す必要はありません。

デバイスがないとサービスは休止します。10 分間デバイスが接続されないと、エージェントのセッションからの収集をやめます。Claude Code と Codex のポーリング、会話履歴の監視、使用量の読み取りを止め、デバイスが接続した瞬間に再開します。このことは service.dormancy で知らせ、"*" にも含まれます。同じオブジェクトが snapshot.service.dormancy にもあり、service.info は collecting と dormant_since を持ちます。

{"jsonrpc":"2.0","method":"event","params":{
  "type":"service.dormancy","rev":140,
  "data":{"window_s":600,"collecting":false,"dormant_since":"2026-11-11T01:51:00.000Z"}
}}

dormant_since は、収集中と、デバイスが一度も接続されていないときは null です。待つべきデバイスなしで起動したサービスは、オブジェクト全体に null を送ります。休止中も、あなたの接続、エージェント、呼び出すすべてのメソッドはこれまでどおり動きます。アプリが自分でセッションから収集している場合は、同じようにしてください。Omarchy ブリッジは、device.link がデバイスなしと伝えてから 10 分たつと、ページへのデータ送信とセッションの確認をやめ、接続すると再開します。

連携のチェックリスト

公開する前に次をテストしてください。両方の画面での最初のチャットと続きのメッセージ、バックエンドが拒否し agent.order.result で報告した指示、コンパニオンによる文字起こしとそのローカルの代替（提供する場合）、ほかのアプリがあるときのあふれ、サインアウトと再接続、ストリーミング中のメッセージの置き換え、古い質問への押下、複数選択のページ送り、キャンセルと送信、バックエンドでの送信の失敗、読み取り専用の設定、思考の深さのカタログが異なるモデルへの切り替え、期限切れの設定の確認。

実行できるサンプルは、tools/tests/test_native_companion.py で偽のバックエンドを使ってもテストしています。公開のリクエストスキーマとメソッドの権限は deckd api-doc から生成しています。独自のエージェントがファームウェアのフォークや Conol のアカウントを必要としないよう、これらのインターフェースはプロバイダー固有のフックと分けておいてください。
