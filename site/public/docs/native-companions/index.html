Native companion API

Native integrations for any agent

Build a native companion for any agent. Your application owns its conversations and model connections; OpenWalkieTalkie supplies a grouped deck roster, voice input, conversation display, questions and session settings. Conol uses this same public interface.

Requires OpenWalkieTalkie app, service and firmware 0.11.0 or newer. This is a local desktop integration over JSON-RPC, with no Conol dependency. Existing CLI hooks remain supported.

Try the example

Start OpenWalkieTalkie, connect your deck, download the example, then run:

python3 native_companion.py

Python 3.10+ is sufficient; no packages or credentials are required. Select Example → + New chat and dictate a first message. The new conversation opens on the deck. Say “form” to try a paged single-choice question, multiple selections, dictated text and a final review. Open the session settings to switch between two scripted demo models and their effort options. The example makes no model API calls. Ctrl-C releases its registrations.

The example's Companion.order, Companion.apply_settings and form submission branch are the places to connect your backend. It keeps a small transcript and form drafts in memory; a production app should restore them from its own conversation store. Run one demo at a time, since both copies use the “Example” device heading.

Connect and discover

Connect from your desktop process to the same-user Unix domain socket. Send one UTF-8 JSON-RPC 2.0 object per newline, using a distinct request id. Correlate replies by id; notifications can arrive between replies. Keep heartbeats running while backend work is in progress.

  • Override: $DECKD_DATA_DIR/deckd.sock, when the variable is set.
  • macOS: ~/Library/Application Support/OpenWalkieTalkie/deckd.sock.
  • Linux socket convention: ${XDG_RUNTIME_DIR}/openwalkietalkie/deckd.sock, falling back to ~/.local/state/openwalkietalkie/deckd.sock. The distributed desktop app currently targets macOS.

Begin every connection with:

{"jsonrpc":"2.0","id":1,"method":"session.hello","params":{
  "client":{"name":"Example companion","version":"1"},
  "scopes":["agent","observe"],
  "subscribe":["agent.order","agent.answer","focus.changed","session.settings_requested"],
  "snapshot":false
}}

The socket authenticates the local OS user. Request only agent and observe for this integration. Owned events include the content needed to handle your conversations; these scopes do not grant another app's private transcript. No remote API key needs to be sent to the daemon. Keep the socket in your trusted desktop process rather than exposing a raw RPC bridge to web content.

A missing socket means the service is unavailable: show a disconnected status and retry with backoff. A -32601 response to either new method means the daemon lacks native companion support; offer an update instead of silently reporting that the integration connected. The service's /v1/schema lists methods and request schemas for clients already using its authenticated HTTP API.

Register sessions and group them

Register one agent per conversation, plus an optional launcher. Keep a stable, namespaced key for each app/account/conversation. Registration is idempotent for that key on the owning connection.

{"jsonrpc":"2.0","id":2,"method":"agent.register","params":{
  "kind":"other","name":"Plan the release","key":"example:personal:chat-42",
  "caps":{"answer":"push","order":"push","focus":true},"lease_ttl_s":30
}}

Save the returned agent ID; use it in subsequent requests. The examples below use ag_example as a placeholder.

{"jsonrpc":"2.0","id":3,"method":"agent.companion.set","params":{
  "agent":"ag_example","profile":{
    "app_id":"org.example.companion","group_id":"personal",
    "group_label":"Example","role":"session"
  }
}}

app_id is a stable application identifier (1–64 ASCII letters, digits, dots, dashes or underscores). group_id identifies an account or workspace within the app (1–128 UTF-8 bytes). group_label is its visible heading (1–24 UTF-8 bytes). Labels and IDs must be nonempty and contain no control characters. These are public presentation fields: use opaque account IDs, not credentials or private account names. Use distinct labels, such as “Example · Work”, for groups that should have separate device pages: the firmware groups by visible label; desktop grouping and overflow promotion use app/account IDs.

role is session or launcher. profile: null removes the native presentation. kind remains the provider identity in the API; use other for a custom agent. Existing provider kinds also accept a companion profile. Conol's optional robot artwork comes from its kind; neither the artwork nor a new firmware enum is required for another app to integrate.

Native focus is routed to your app through events instead of terminal injection. There are eight shared physical slots. Check the returned slot (null means overflow). Focusing an overflow companion first uses normal slot allocation; if all slots are busy, it can replace an unpinned session from the same owning connection, app and group. That fallback preserves launchers, other accounts and other apps. It does not guarantee a slot when all candidates are protected. Do not register an unbounded history: publish a useful active window and retain the full list in your own app.

Send agent.heartbeat with your owned agent IDs every 10 seconds for a 30-second lease. On sign-out or shutdown, use agent.release. After a socket loss, reconnect and register again. If registration returns ownership conflict -32004, agent.claim {"key":"…"} can reclaim an orphaned or expired registration; it cannot take over an active connection. Republish profile, settings, transcript and the current question after reconnect. Neither leases nor the daemon are your persistent chat database.

Start and activate a new chat

Register a launcher named + New chat with role: "launcher" and the same group as its conversations. Its order capability must be push. The role controls presentation and slot protection; it does not create backend sessions for you.

Handle notifications in this envelope:

{"jsonrpc":"2.0","method":"event","params":{
  "type":"agent.order","rev":123,
  "data":{"agent":"ag_launcher","text":"Help me plan the release"}
}}
  1. Resolve data.agent to an owned account and launcher. Deduplicate the notification within this connection, using its rev and type.
  2. Create the conversation and first user message through your authenticated backend. Keep its durable ID; serialize concurrent starts for the same launcher.
  3. Register the new conversation with its own stable key and role: "session". Publish actual settings and recent messages.
  4. Select the new conversation in your app, then call agent.focus {"agent":"ag_new"}. The daemon sends slot replacement updates before focus, and the firmware opens the conversation after PTT release. An already open question card stays put.

Handle focus.changed with data.source: "device" by selecting the matching conversation in your app, or opening a blank composer for the launcher. Do not respond with another focus request and create a feedback loop. Events for unknown agent IDs must be ignored.

Never retry an uncertain backend create blindly. Use your backend's idempotency key or reconcile the durable result first. A socket reconnect is not proof that a previous create failed. The sample's local in-memory creation is illustrative; production backends must supply this guarantee.

Keep both transcripts current

For an existing session, agent.order means deliver a follow-up message to that conversation. Use a stable client message ID in your backend, update your app's visible transcript, and resume its response stream. Mirroring only to the deck leaves your desktop UI stale.

Publish public user and assistant messages with stable IDs:

{"jsonrpc":"2.0","id":4,"method":"agent.reply","params":{
  "agent":"ag_example","text":"I can help with the release.","speak":false,
  "message":{"id":"message-42","role":"assistant","streaming":true}
}}

Send the same message ID to replace the text during streaming; finish with streaming: false. Send user messages with role: "user" too. The daemon retains at most 64 messages and 512 KiB per agent; publish a bounded recent window. Keep private reasoning, credentials and internal tool arguments out of the mirrored transcript. Speech is opt-in through speak.

Use agent.update for the conversation name, short title and state (working, question, ready, error or idle). Preserve the actual backend state and surface delivery failures without claiming a message was accepted.

Handle complex questions on the deck

The public question primitive is agent.card.set. A card can have up to four choices and optional free text. Build a multi-step form in your application; every rendered step gets a new card ID.

{"jsonrpc":"2.0","id":5,"method":"agent.card.set","params":{
  "agent":"ag_example","type":"q","text":"1/3 Choose a language",
  "choices":[{"label":"Python"},{"label":"Rust"},{"label":"More"},{"label":"Cancel"}],
  "free_text":false,"deliver":"push","origin":{"kind":"custom"}
}}

Save result.card.id. Accept agent.answer only when both data.agent and data.card match the active question. data.choice is a zero-based choice index; data.text carries dictated free text. Never apply a late answer to a replacement question. Clear the previous card with agent.card.clear {"agent":"…","card":17,"delivered":false} before publishing the next step.

  • Page long choice lists instead of truncating them. Reserve buttons for navigation.
  • Implement multiple selection as toggles, keeping selections across pages until Next.
  • Use a dedicated free_text: true step for typed/dictated answers or an Other option.
  • Keep drafts locally. Review the full answers with Submit, Edit and Cancel.
  • Only Submit sends the answer envelope to the exact pending tool call or approval in your backend. Navigation, edits and cancellation must not approve anything.
  • Confirm delivery only after the backend accepts submission. On failure, retain the draft and reuse a stable submission ID for an explicit retry. Recheck that the backend question is still pending after reconnect.

If a form cannot be represented within the device limits, offer an explicit “Open in app” choice. The app should focus the relevant question, without pretending the form was completed. The example demonstrates the wizard using a scripted local form; Conol connects the same pattern to AskUser and workflow approvals.

Display and change model / thinking effort

Report settings with agent.session.set for any owned agent. Display-only settings need no catalog:

{"jsonrpc":"2.0","id":6,"method":"agent.session.set","params":{
  "agent":"ag_example","controls":{
    "model":"My model","effort":"High","editable":false,
    "note":"Change these settings in Example."
  }
}}

For deck-editable settings, supply stable model IDs, readable labels and each model's supported effort values. Send the backend's actual selection, not a guessed default.

{"jsonrpc":"2.0","id":7,"method":"agent.session.set","params":{
  "agent":"ag_example","controls":{
    "model":"fast","effort":"low","editable":true,"note":"",
    "models":[
      {"id":"fast","label":"Fast model","efforts":["low","high"],"default_effort":"low"},
      {"id":"simple","label":"Simple model","efforts":[],"default_effort":""}
    ]
  }
}}

model and each model ID/label are limited to 128 UTF-8 bytes; effort strings to 32; note to 256. There may be at most 64 models and 16 efforts per model, with unique model IDs and unique effort values. Control characters are rejected. Editable selections must belong to their catalog; empty effort represents the backend default or no effort setting. A nonempty default_effort must be listed in that model's efforts.

A device selection emits session.settings_requested (underscore before requested):

{"jsonrpc":"2.0","method":"event","params":{
  "type":"session.settings_requested","rev":124,
  "data":{"agent":"ag_example","model":"fast","effort":"high","request_rev":19}
}}

Apply the requested setting in your backend, then call agent.session.set with the actual resulting controls and request_rev: 19. Use data.request_rev, not the envelope's event rev. The device keeps its existing selection pending until confirmation. On failure, confirm the unchanged actual settings with a short explanatory note.

Ordinary refreshes omit request_rev and do not settle pending requests. A mismatched, duplicate or expired confirmation is rejected. Pending changes time out after 45 seconds. Preserve request/agent correlation across asynchronous work, and reconcile the backend if a response is lost. The daemon validates transport and ownership; your application remains responsible for authorizing and applying model changes.

Integration checklist

Before shipping, test a first chat and follow-up on both screens; overflow with another app present; sign-out and reconnect; streamed message replacement; stale question presses; multi-select paging; cancel versus submit; backend submission failure; readonly settings; model changes with different effort catalogs; and an expired settings confirmation.

The runnable example is also checked with a fake backend in tools/tests/test_native_companion.py. The public request schemas and method permissions come from deckd api-doc. Keep these interfaces separate from provider-specific hooks so a custom agent does not need a firmware fork or a Conol account.
