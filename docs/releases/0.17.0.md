OpenWalkieTalkie 0.17.0 fixes dictation on Windows. On the Windows preview, a press of PTT produced no text: the recogniser ran out of time before it finished. It now finishes in about a second.

The deck's firmware is unchanged: it stays at 0.14.0. Nothing changes on macOS or Omarchy.

## What was wrong

On Windows, Whisper runs on the CPU. Two things made it far too slow there:

- **whisper.cpp was compiled with no optimisation.** With the Visual Studio generator, the `cmake` crate overwrites `CMAKE_C_FLAGS_RELEASE` and `CMAKE_CXX_FLAGS_RELEASE` with flags that carry no `/O2`, so the release build of the Windows preview shipped a whisper.cpp built with `<Optimization></Optimization>`: no optimisation at all.
- **Windows used the Mac's decode settings.** Linux already tells Whisper how much of its 30-second window is audio and makes one pass instead of retrying at higher temperatures. Windows took the Mac's defaults, which suit Metal: the encoder ran its full 30-second window for a 2-second press, and a failed pass was decoded again.

Together, a short press could take longer than the 30 seconds a dictation is given, and then no text came out at all.

## What changed

- The release workflow's Windows build sets `CMAKE_C_FLAGS_RELEASE` and `CMAKE_CXX_FLAGS_RELEASE` to `-O2 -Ob2 -DNDEBUG`, so whisper.cpp is compiled optimised.
- On Windows, as on Linux, Whisper makes one pass and encodes only as much of its window as the press needs.
- When the model loads, the service's log records which CPU features whisper.cpp was compiled with (`whisper stt: system info`). Each decode's time, audio length, encoder window and thread count are logged at debug level (`whisper stt: decode`), never the words.

## How it was verified

On a Beelink EQ mini PC (Intel Core i5-13420H, 8 cores / 12 threads, 31.8 GB RAM) with the `ggml-small.bin` model, `language = "zh"`, and a deck on USB, the same sentence, 「收到，已经下发了。」, was spoken into three builds:

| Build | Result |
| --- | --- |
| 0.16.0 as shipped (unoptimised whisper.cpp, Mac decode settings) | No text. Two presses, one with `small` and one with `large-v3-turbo-q5_0`, both ended `stt: final decode failed; nothing sent error=speech recognition timed out after 30000 ms` |
| Linux decode settings, whisper.cpp still unoptimised | Text came out after 17,242 ms (`stt: final decode completed decode_ms=17242`); the two decodes took 8,867 ms for 1.1 s of audio (`ok=false`) and 9,987 ms for 2.5 s (`ok=true`) |
| 0.17.0 (both fixes) | 1,124 ms (`stt: final decode completed decode_ms=1124`); the decode took 1,115 ms for 2.2 s of audio (`audio_ctx=512 threads=8 ok=true`) |

That is faster than the reference `whisper-cli` 1.8.3 on the same CPU, which took 1.7 to 1.9 seconds for a 3.9-second clip.

The 0.17.0 transcript was `收到已经下发了`: all seven characters correct, in order and in Simplified Chinese. The comma and the final full stop were left out.

## Building on Windows yourself

A local Windows build must set the same two variables, or whisper.cpp is compiled unoptimised again: in the test above, a decode took about nine times as long. In PowerShell:

```powershell
$env:CMAKE_C_FLAGS_RELEASE = "/O2 /Ob2 /DNDEBUG"
$env:CMAKE_CXX_FLAGS_RELEASE = "/O2 /Ob2 /DNDEBUG"
cargo build --manifest-path host/Cargo.toml -p deckd -p openwalkietalkie-app --release --locked --target x86_64-pc-windows-msvc
```

In Git Bash, write them with dashes (`-O2 -Ob2 -DNDEBUG`): Git Bash rewrites a value that starts with a slash as a path. Setting them under `[target.'cfg(windows)'.env]` in a cargo config does not work (cargo ignores it), and setting `_CL_` instead breaks CMake's compiler detection. The `whisper stt: system info` line in the log shows the CPU features the build was compiled with.

## Update

On Windows, download the ZIP from the release. On a Mac, choose **Check for Updates…**, or install the signed, notarized **0.17.0** app for Apple Silicon or Intel (macOS 13 or later). On Omarchy, pull, build the service and the app, and run `install.sh` with both, as the [Omarchy guide](https://openwalkietalkie.org/docs/omarchy/) shows. The deck needs no firmware update for this release.
